What is the eMudhra certificate issue?

Perhaps because PHP vulnerability issues were announced around the same time, this issue has not received much attention among people around me. However, a very serious certificate-related problem was discovered on 2026/10/20.

eMudhra Intermediate CA Compromise

To explain the eMudhra issue briefly:

  • There was a configuration error in the process of creating SSL certificates, which prove that a website or application is genuine.
  • Private keys that should have been generated using sufficient randomness ended up with extremely small values, such as 4 or 56, due to the configuration error.
  • As a result, the corresponding private keys could be easily recovered from publicly available certificates.

That's the issue.

## What should we do?

Programs need to be updated so that they no longer trust the affected certificates. This includes web browsers and programs that communicate using SSL/TLS.

Web browsers (Chrome, Firefox, etc.)

Browser vendors blocked the affected intermediate CA certificates using mechanisms such as CRLSet and OneCRL, without waiting for updates to the browser applications themselves.

How to check

Access Does your client still trust the compromised intermediates? and check that the result for every listed Intermediate CA is ✅ Did not connect.

If this is not the case, update your web browser and check again.

※ If you continue using a browser that does not show ✅ Did not connect, you may mistake a malicious attacker's website for a genuine one and suffer a security incident. You should stop using the browser until the issue is resolved.

Programs other than web browsers

Many programs other than web browsers also use certificates to establish connections (Java, Python, Go, curl, Linux OS, etc.).

Unlike web browsers, other programs do not necessarily receive and apply certificate blacklists through a common mechanism. Some use the OS certificate store, while others use their own certificate stores. Therefore, countermeasures and verification are required depending on each program and its execution environment.

If no action is taken, these programs will continue to trust the compromised eMudhra keys as genuine (safe).

The impact on general users may be limited, but IT departments, system administrators, and infrastructure engineers need to update various systems.

In the case of curl

First, I will show the results of testing with everyone's favorite curl.

※ Programs and operating systems with available patches are listed at Who has patched?. Please refer to that page for details on each product.

First, I ran curl against one of the sites listed on Does your client still trust the compromised intermediates?.

$ curl https://dv-g3b-emudhra.we-have-a-problem.com/
Your client successfully connected to the site. That's bad!

That's bad!

Let's see if updating the packages solves the problem.

$ sudo dnf update -y

Run the command again after the update.

$ curl https://dv-g3b-emudhra.we-have-a-problem.com/
Your client successfully connected to the site. That's bad!

It did not work.

It seems that a patch is not yet available in the Rocky Linux repositories (as checked at 11:00 JST on 2026/10/22), so I will apply a manual workaround.

Let's add the certificate to the blacklist and disable it. The procedure is as follows.

First, check the subject.

$ echo | openssl s_client \
> -connect dv-g3b-emudhra.we-have-a-problem.com:443 \
> -servername dv-g3b-emudhra.we-have-a-problem.com 2>/dev/null \
> | openssl x509 -noout -issuer -subject

issuer=C = NL, O = eMudhra BV, CN = EM DV TLS CA - G3B
subject=CN = dv-g3b-emudhra.we-have-a-problem.com

Add the certificate to the blacklist.

vi /etc/pki/ca-trust/source/blacklist/emudhra-g3b.pem

Save the contents of the intermediate CA certificate obtained above (from -----BEGIN CERTIFICATE----- to -----END CERTIFICATE-----).

You can also do it as follows.

cat > /etc/pki/ca-trust/source/blacklist/emudhra-g3b.pem <<'EOF'
-----BEGIN CERTIFICATE-----
MIIDaDCCAu6gAwIBAgIQAKSu5njyM2K0wORgt3LyFDAKBggqhkjOPQQDAzBWMQsw
...
gt2TlfJbHii+KNvK
-----END CERTIFICATE-----
EOF

After adding it to the blacklist, apply the changes.

sudo update-ca-trust

sudo trust extract-compat

Check whether it is blacklisted.

It shows trust: blacklisted.

$ trust list | grep -A5 -B5 "EM DV TLS CA - G3B"

    type: certificate
    label: EM DV TLS CA - G3B
    trust: blacklisted

$ curl https://dv-g3b-emudhra.we-have-a-problem.com/
Your client successfully connected to the site. That's bad!

No change...

Let's try wget as well.

$ wget -O - https://dv-g3b-emudhra.we-have-a-problem.com/

It seems that adding the certificate to the blacklist was successful.

trust list shows EM DV TLS CA - G3B as trust: blacklisted, and wget also reports certificate errors.

On the other hand, curl and openssl s_client still seem to consider the certificate valid.

At least for wget, I was able to confirm that the blacklist is working.

Since I don't directly use curl in the systems I am responsible for, I think I'll wait for further action from the Rocky/RHEL side... probably.

※ Tested on Rocky 8.10 and Rocky 10.2.
